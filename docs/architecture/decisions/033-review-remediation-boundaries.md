# 033 Исправление границ операций после архитектурного ревью

- Status: Accepted
- Date: 2026-10-05
- Scope: устранение находок ревью `a0cf2d866`, сохранность данных и согласованность сессий

## Контекст

Исходный набор из 679 тестов проходит, но независимое ревью выявило проверяемые сценарии потери данных и несогласованности состояния. Пользователь поручил реализовать исправления и обновить Spec Harness. Это Complicated decision: причины можно установить чтением кода и воспроизводящими проверками.

Критерии происходят из контрактов проекта: сохранность прогресса, изоляция пакетов, неизменность правил mastery/навигации, поддержка старых сохранений и проверяемость реальных UI-путей. Рассмотрены три независимых варианта: адресные изменения текущих владельцев; общий слой транзакций/lifecycle/контекста; ограниченные изменения по проверяемым этапам.

## Сравнение вариантов

Оценки от 1 до 5 отражают ожидаемые свойства подхода, а не доказанные результаты реализации.

| Вариант | Корректность и данные 40% | Контроль регрессий 30% | Обратимость 15% | Стоимость 15% | Итог |
|---|---:|---:|---:|---:|---:|
| Адресные исправления существующих владельцев | 4 | 4 | 5 | 5 | 4.30 |
| Общие контракты для транзакций, lifecycle и контекста | 5 | 2 | 2 | 1 | 3.05 |
| Ограниченные исправления по этапам с сохранением публичных контрактов | 5 | 5 | 5 | 3 | 4.70 |

Первый и третий варианты близки. Выбран третий с адресной реализацией первого: его небольшие проверяемые этапы позволяют локализовать и откатывать ошибки. Общий framework не создаётся; специализированный владелец операции допустим, если нужен для полного охвата её эффектов, даже при одном потребителе.

## Решение

Сохранить один runtime, текущие форматы хранилищ и публичные facade. Исправить границы import/restore, переходы сессии и callback identity. Перенести воспроизводящие проверки в поддерживаемые тесты. Закрывать полные инварианты операций, а не отдельные строки с симптомом. Порядок и проверяемые условия определены в [плане](../../plans/2026-10-05-architecture-review-remediation.md).

## Проверка рисков и возражение

Pre-mortem: строгие валидаторы отвергли настоящие старые backup; staging всё ещё менял сторонние индексы до проверки; reset потерял настройки или повторно начислил credit; удаление legacy сломало доступный импорт; локальные ZIP скрыли невоспроизводимость чистого checkout.

Независимый Red Team указал, что поэтапность сама по себе не делает импорт целостным, а оценки 5 пока являются ожиданиями. Возражение принято: до изменения импортера перечисляются все его записи и удаления; validation и сохранность предыдущей версии выпускаются вместе. Старые backup проверяются на форматах реальных сериализаторов. Rollback исключения не называется защитой от process death без отдельной проверки восстановления. Изъятие старого CSV path допускается только после рабочего pack-based импорта. Финальная сборка проверяет Git-входы отдельно от текущего каталога.

## Последствия и журнал решения

Сложность существующих ViewModel частично остаётся, зато каждое исправление связано с конкретной регрессией и ограниченным изменением. Новые необязательные функции и включение Daily в эту работу не входят.

### Дополнение: происхождение карточки при совпадающих CSV ID

Повторная проверка реальных EN_WORD_ORDER_A1 и EN_WORD_ORDER_A1_DRILLS выявила одинаковый `card_2` у разных предложений. Глобальное скрытие по этому ID скрывает чужую карточку. Смешанное повторение также не может определять исходный урок по совпавшему ID и выбранному сейчас уроку.

Рассмотрены три варианта: фильтровать только по выбранному уроку (малое изменение, но неверно для подмешанных карточек); переименовать все persisted card IDs (широкая миграция mastery и сохранений); добавить происхождение карточки в runtime и отдельный scoped key для скрытия (выбран). Независимые проверки владельцев данных и сессий сошлись на третьем варианте: он сохраняет существующие card IDs и требует проверки источника при смешанном повторении. При прежних весах ожидаемые оценки (сохранность / регресс / обратимость / стоимость): 2/2/4/4 → 2.60, 4/3/2/1 → 3.05, 5/4/5/3 → 4.40 соответственно; это оценки риска, не результаты тестов.

Источник задаёт каталог: pack и lesson сопровождают карточку через копирование/перемешивание. Скрытие, новые жалобы на предложения и начисление освоения используют действительный источник; scoped clear не меняет другой пакет. Исторические жалобы остаются экспортируемыми без угадывания урока. Исторический голый `card_N` не позволяет восстановить намерение пользователя: запись сохраняется как непривязанная, но не применяется глобально ко всем курсам. Это может снова показать ранее скрытую карточку; без исходного контекста безопасно восстановить её принадлежность невозможно. Формат mastery и его ключи не переименовываются. Ранее ошибочно начисленное освоение также не перераспределяется: исходный урок нельзя достоверно вывести из старой записи. Обязательные регрессии: два реальных пакета, два урока с одинаковыми ID, подмешанная карточка и владение credit, старый hidden snapshot и новый scoped roundtrip.

Общая report sheet показывает только реализованные действия. Для Vocab прежний Hide лишь закрывал окно; для Verb/Aux он пропускал текущую карточку, но следующий deck не читал hidden store. Выбран явный отсутствующий callback и отсутствие кнопки в этих режимах. Расширять drill scheduling новой функцией скрытия в рамках исправления не требуется. Для обычных предложений остаётся действующий Hide с проверкой источника. Регрессии активируют настоящие report controls и отдельно проверяют доступность действия и его сохранённый эффект.

Ожидание на 30 и 90 дней: новые изменения import/restore/context сохраняют все добавленные regression assertions; отсутствуют независимые записи прогресса без нужного pack/card identity; включённые asset inputs воспроизводятся из Git. Проверять при следующем изменении этих владельцев и перед следующим слиянием. Настоящую пригодность решения устанавливают финальные тесты и последующая эксплуатация, а не оценки матрицы.
